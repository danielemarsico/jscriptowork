# Air-gap file transfer with Decimen — runbook

Move files between an **air-gapped laptop** and a **phone** with no network, no
cloud, and no USB stick — the payload travels only as light (animated QR codes),
using [Decimen Optical Transfer](https://github.com/bashalarmistalt/decimen-optical-transfer).

The one hard part is the chicken-and-egg: the laptop needs Decimen's sender on
it *once*, and you won't plug in a USB stick that might be infected. This runbook
solves that with an **ESP32 in USB-HID (keyboard) mode** that types the sender in
as verified chunks — generated by
[`examples/esp32-decimen-loader.js`](esp32-decimen-loader.js) in this repo.

After the bootstrap, the laptop only ever *sends* (displays QR); the phone
*receives* with its camera. The laptop never needs the ESP32 again.

Only the **generator** touches jscriptowork, and only on the online PC. The
transfer itself (Decimen), the bootstrap device (any USB-HID board), and the
air-gapped laptop (built-in Windows tools only) do not — so this plan is
portable and reusable on its own.

## How the chunks actually travel

The chunks are **not** copied as a file. The HID device *types* them, like a
very fast human at the keyboard. Nothing is mounted on the laptop — a keyboard
can only send keystrokes, so it cannot drop an infected file on it.

```
ONLINE PC                      HID DEVICE                 AIR-GAPPED LAPTOP
─────────                      ──────────                 ─────────────────
generator makes the      →     flash it: the        →     (carry device over,
 line list / sketch             chunks now live in          plug into USB)
 (chunks are text)              the device's flash               │
                                                                 ▼
                               device = a keyboard   →     types each line into
                               that remembers what          a Command Prompt,
                               to type                       then presses Enter
                                                                 │
                                                                 ▼
                                                           25 small files on disk
                                                           → joined, decoded,
                                                             unzipped → the .html
```

One chunk is one typed line, e.g. `>p07.b64 echo UEsDBBQ…` — when typed and
entered, the laptop writes that text into `p07.b64`. Do that for every chunk,
then join + decode + unzip. **Plugging in the device and pressing the button is
the transfer; the typing is the delivery.**

---

## What this protects, and what it doesn't

- **No network path between the two devices.** The transfer is light only.
- **No storage medium touches the laptop.** The ESP32 is a keyboard: it carries
  no filesystem the laptop could autorun. Every command it types is visible on
  screen, and the file is SHA-256 verified before you trust it.
- **The optical channel is not encrypted.** Any camera that can see the sending
  screen can read the file. Decimen gives you *no network*, not confidentiality —
  don't stream secrets in a room you don't trust.
- **The receiver on the phone runs code.** If it's the public app, it can update
  itself. Receive in **airplane mode**, and prefer a receiver you host yourself
  (Phase 6) if that's in your threat model.

## Decisions already taken

- **Sender: English-only build (~96 KB).** Halves the typing versus the stock
  249 KB multi-language build. It needs a one-time rebuild (Phase 1).
- **Keyboard layout: US or US-International.** The generator emits **no
  double/single quotes, backticks, carets or tildes**, which are the only
  dead-key characters that differ between those two layouts. base64 itself is
  all `A–Z a–z 0–9 + / =`, none layout-sensitive. So both layouts work
  unchanged.
- **ESP32-S2 or ESP32-S3** (native USB HID). A classic ESP32 has no native USB;
  it would need BLE-HID or an add-on, which this runbook doesn't cover.

## Phase 0 — Prerequisites

**Air-gapped laptop:** Windows 10 1803+ or Windows 11 (for `tar.exe` and
`certutil.exe`, both built in); Chromium-based Edge (ships with Windows); note
its keyboard layout.

**Online PC** (never the air-gapped one): Windows with jscriptowork checked out;
Node.js 24 (only to *build* the English-only sender in Phase 1); the Arduino IDE
with ESP32 board support (to flash the ESP32).

**Hardware:** an ESP32-S2 or S3 dev board with a BOOT button (almost all have
one).

## Phase 1 — Build the English-only sender (online PC)

1. Clone Decimen and check out the release you want:
   ```
   git clone https://github.com/bashalarmistalt/decimen-optical-transfer
   cd decimen-optical-transfer
   git checkout v0.5.3        # or the latest tag
   ```
2. Two edits make it English-only:
   - `shared/i18n/loaders.inline.ts` — replace the twelve `import`s and the
     `loaders` map with just English:
     ```ts
     import type { Messages } from "./messages";
     import * as en from "./locales/en";
     export const loaders: Record<string, () => Promise<{ messages: Messages }>> = {
       en: () => Promise.resolve(en),
     };
     ```
   - `shared/i18n/registry.ts` — trim `LOCALES` to the single `en` row.
3. Build the standalone pages:
   ```
   npm ci
   npm run build:standalone
   ```
   The sender is `dist-standalone/decimen-sender.html` (~96 KB, essentially
   all ASCII). The receiver is `dist-standalone/decimen-receiver.html`.

> Prefer zero build? Skip Phase 1 and feed the **stock** `decimen-sender.html`
> from the release's assets to Phase 2 instead — it just takes ~3× longer to
> type (~128 K characters, still well under 30 minutes).

> **Licence:** Decimen is AGPL-3.0. Using a modified build for yourself carries
> no obligation; only *distributing* the modified version to other people does.

## Phase 2 — Generate the ESP32 sketch (online PC, via jscriptowork)

```
cscript bin\launcher.js examples\esp32-decimen-loader.js path\to\decimen-sender.html --out C:\loader
```

Options: `--chunk <n>` base64 chars per chunk (default 1800), `--keyms <n>`
per-key delay (default 8), `--linems <n>` per-line delay (default 120).

It prints **SELF-CHECK OK** (the chunks decode back to the zip byte-for-byte)
and writes to `C:\loader`:

- `esp32-decimen-loader.ino` — the sketch to flash.
- `manifest.txt` — the source SHA-256, chunk count, and the run procedure.

What the sketch will make the laptop do, using only built-in Windows tools:

1. Type each base64 chunk into its own file and check it on the spot with
   `certutil` + `findstr` (`Pnn OK` / `Pnn BAD`).
2. `copy /b` the chunks together, `certutil -decode` the base64, `tar -xf` the
   zip.
3. `certutil -hashfile` the result and compare to the original — printing
   **FILE OK**.

A **canary** line (every base64 symbol, hashed) is typed first, so a wrong
keyboard layout shows up as `CANARY BAD` before any real payload is typed.

---

## Phase 3 — Flash the ESP32 (online PC)

1. Arduino IDE → select your ESP32-S2/S3 board.
2. Enable native USB HID: set **USB Mode** / **USB CDC On Boot** as your core
   requires (varies by board; the goal is that `USBHIDKeyboard` enumerates as a
   real keyboard).
3. Open `esp32-decimen-loader.ino`, upload.

---

## Phase 4 — Dry run (a NON-air-gapped PC, same layout)

Do this once before touching the real laptop:

1. Plug the ESP32 into a spare Windows PC set to the **same layout** as the
   laptop.
2. Open a Command Prompt, click into it.
3. Press **BOOT** once → watch for `CANARY OK`. If `CANARY BAD`, the layout is
   wrong; fix it and press BOOT again.
4. Press **BOOT** again → watch the `Pnn OK` lines and the final `FILE OK`.
5. Time it and, if you like, lower `--keyms` and regenerate for speed. Any
   `Pnn BAD`: press RESET and repeat from step 3 (every chunk file is
   overwritten, so a clean re-run is idempotent).

---

## Phase 5 — The real transfer (air-gapped laptop)

1. Disable sleep/screensaver; confirm Caps Lock is off; don't touch the keyboard
   while it types.
2. Open a Command Prompt, click into it.
3. **BOOT** once → `CANARY OK`.
4. **BOOT** again → wait for `FILE OK`.
5. The sender is now at `%TEMP%\dcm\decimen-sender.html`. Move it somewhere
   permanent, e.g. `C:\tools\decimen\`.
6. Re-verify any time:
   `certutil -hashfile C:\tools\decimen\decimen-sender.html SHA256`
   and compare to the `source SHA-256` in `manifest.txt`.
7. Make a shortcut to launch it in app mode:
   `msedge --app=file:///C:/tools/decimen/decimen-sender.html`

---

## Phase 6 — The receiver (phone)

Two options, from easiest to most private:

- **Public app:** open [decimen.app](https://decimen.app/) once, install it
  (Android: *Install app*; iOS: Share → *Add to Home Screen*). Works offline
  afterwards. Receive in **airplane mode**.
- **Self-hosted (recommended if you don't want auto-updating code):** deploy the
  Decimen *site* build (`decimen-…-site.zip` from the release, unmodified) to
  your own domain over HTTPS, add a strict Content-Security-Policy limiting it to
  `self`, and install from your URL. A phone camera needs a real HTTPS origin, so
  a local `file://` receiver won't work — the site or your domain is the way.

---

## Phase 7 — First transfer & upkeep

1. Send a small test file first, phone in airplane mode. After receiving media,
   tap **Clear Decimen cache** on the phone.
2. On a new Decimen release: read its changelog and the compatibility table in
   Decimen's `docs/technical/versioning.md`. Update **both sides together** —
   rebuild the sender (Phases 1–2, re-type via Phase 5) and redeploy the
   receiver — and record the new SHA-256 in your notes. Sender and receiver must
   come from the same release so their frame formats match.

## Using a different HID device (Raytac dongle, Pi Pico, Rubber Ducky…)

Nothing here is ESP32-specific except the emitted `.ino`. The generator also
writes **`payload-lines.txt`** — the exact lines to type, in order, with the two
stages marked. Any USB-HID device can replay that list; only the "type these
lines, press Enter, wait for a button between the two stages" firmware differs.

- **nRF52840 / Raytac dongle** — flash a USB-HID keyboard firmware (Adafruit
  nRF52 Arduino core, or Zephyr), read the lines from `payload-lines.txt`, and
  send each with a small per-key delay. A GPIO button triggers stage 1, then
  stage 2 — exactly like the ESP32 BOOT button in this runbook.
- **RP2040 / Raspberry Pi Pico** — CircuitPython's HID keyboard library, or
  Arduino `Keyboard`.
- **Hak5 Rubber Ducky / O.MG** — convert the lines to DuckyScript
  (`STRING <line>` then `ENTER`, with a `DELAY` between the two stages).

Whatever the device, keep the two invariants that make it safe and reliable:

1. **A pause between stage 1 and stage 2**, so you can confirm `CANARY OK`
   (correct keyboard layout) before the payload is typed.
2. **Type the lines verbatim** — they already avoid every dead-key character, so
   set the device to a US or US-International layout and don't remap anything.

The per-chunk `certutil`/`findstr` checks and the final SHA-256 are in the lines
themselves, so integrity does not depend on the device — a slower or flakier
board just means re-running, never a corrupt file that passes silently.

## Reference: how the loader stays safe to type

- Commands are quote-free and use redirect-first `>file echo …`, so no dead-key
  characters are ever emitted (US and US-International both work).
- Every chunk is hashed on the laptop and compared before assembly, so a dropped
  or mistyped keystroke is caught where it happened.
- The final file is SHA-256 checked against the original; `FILE OK` is the gate.
- The generator self-checks that its chunks decode back to the source before it
  writes anything.
